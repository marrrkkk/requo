# UUIDv7 for new entity IDs; text PKs and existing IDs stay stable

All newly created Requo-owned entity IDs are UUIDv7 strings generated app-side through `newEntityId()` (`lib/ids.ts`, built on the existing `uuid` dependency). Existing rows keep their current IDs byte-for-byte and columns stay `text` PKs — no data migration, no type rewrite — so history is mixed (`prefix_hex` and v4 from before, v7 going forward) and IDs remain opaque everywhere (never displayed, never parsed; only the unrelated `optimistic_` client prefix is ever branched on).

We chose app-side v7 over database-native generation so ID creation stays independent of the Supabase Postgres version, and v7 over keeping prefixed IDs so new identity carries no entity type and gains time-ordering for index locality. The alternatives rejected: rewriting existing PKs (breaks stable identifiers for no technical gain), native `uuid` columns (migration risk without a concrete need), and reformatting document numbers (customer-visible continuity wins — `Q-NNNN`, `INV-NNNNNN`, `PAY-YYYY-NNNN` are preserved verbatim; inquiries stay ID-only with no human number).

Out of scope by design: Better Auth-owned tables (library-generated identity), external provider IDs (`billing_events.providerEventId`, Stripe/Polar columns — separate columns, never overwritten), ephemeral tokens/keys/paths, JSONB config element IDs, and draft correlation IDs (`qgen`, staged `prop_` proposals). Validation stays `string` (never `.uuid()`) because legacy rows hold non-UUID values. Quote/invoice numbering needed no change: both already allocate under a unique constraint with conflict retry, and payments use the locked counter from ADR-012. Verify production-data status against the live database before any deploy that assumes otherwise.
